# MECC 实验补全总计划

> 制定时间：2026-11-03。目标是把当前组会 PPT 和 DAC 论文中的**实验图**逐张替换为可追溯的真机结果。本计划是路线图；每一轮上机前还须发布冻结的配置、命令和停止条件。执行规范以 [EXPERIMENTS.md](EXPERIMENTS.md)、[PROVENANCE.md](PROVENANCE.md) 和 [WORKBUDDY_A100_RUNBOOK.md](WORKBUDDY_A100_RUNBOOK.md) 为准。
>
> 当前 PPT 的数值来源是 `mecc_package/paper/dac2027/ideal_assumptions.json`，其状态为 **HYPOTHETICAL DESIGN TARGETS**。只有通过本计划的证据门禁后，才能把某个图格替换为实测值；不得把占位数值与实测数值混成一张“实验结果”图。

## 1. 终点与现状

**完成定义**：每张保留的实验图都有明确问题、冻结的模型/输入/策略/预算、至少三次独立运行的原始数据、失败记录、统计方法、图像生成脚本和 `PROVENANCE` 登记。图上的每根柱、每个点和误差线，都能追溯到报告中的 run ID。论文和组会版中的相同指标使用同一份数据。

截至本计划制定时，最新已审查的 Workbuddy 结果为 `gpu/a100-copy-readiness-20261103@5345a04`：L0、短窗 PPL 和 4×16 稳定性诊断完成；相同的 77-token 内置文本上，两种 fp16 策略 PPL 相同，近失缓冲保持零。**这些是诊断，不是正式性能图的数据。**

仍待关闭的硬问题：

1. **正确性**：短窗 PPL 相同不等于逐层路由、logits、生成 token 相同；`skip_ppl=true` 的字符串 `exact(lossless)` 是占位值。
2. **容量公平**：相同逻辑缓存槽数尚未证明相同物理 GPU/CPU 字节；镜像、锁页内存、临时缓冲及预取均须计入。
3. **计量口径**：warmup、prefill、decode、PPL 的命中与实际 SSD/H2D/D2H 字节需要拆开；需求读取与预取要分开。
4. **存储介质**：`/data` 是本地 ext4 块设备，但 RAID 背后的介质类型为 `unknown`，目前不能称为 NVMe SSD 性能。主表若声称 SSD/NVMe，必须获得设备证据，或迁移到可确认的 SSD/NVMe 后按冻结协议重跑。
5. **输入**：WikiText-2 下载失败会回退到内置文本；正式实验必须使用离线固定输入及其 token 哈希，画像与评估样本分开。
6. **资源**：单张 A100 无法提供 2/4/8 卡实测。Mixtral-8×22B、Qwen2-57B-A14B 的权重、loader、存储和落 SSD 条件尚未通过门禁。

## 3. 必须按顺序完成的阶段

### G0：冻结实验契约（本地设计，Workbuddy 只做主机确认）

- 固定代码 commit、Mixtral snapshot/tokenizer/store manifest、fp16、确定性生成设置、`cold_ssd`、预算和预取开关。保留现有 50/40 GB 诊断配置作为起点，但正式预算须以**物理峰值**验证后冻结。
- 制作离线输入清单：问答、代码、PPL、画像、任务切换，各自保存数据集名称/版本/split/样本 ID、原文哈希、token ID 哈希与**实际**长度；画像与评估不能重叠。下载失败即停，不自动回退。
- 查明存储设备：由管理员提供 RAID 物理盘清单或提供可验证的本地 SSD/NVMe 路径。记录 `findmnt`、`lsblk`、设备型号、介质类型、空闲容量、直接读测量条件。介质仍未知时仅允许正确性/机制诊断，不发布 SSD/NVMe 性能图。
- 为每个图格建立 `figure_manifest`：模型×任务×策略×预算×重复编号、输入 hash、指标、run ID、期望报告路径。

**出口**：冻结 manifest 经过本地审核；资源条件明确，不能运行的图格标 `blocked`。

### G1：正确性门禁（优先于任何速度对比）

- 本地增加确定性对照工具：同一 checkpoint、输入、精度和路由设置下，对同步 fp16 参考、MECC、fp16 对照逐层记录选中专家 ID、关键中间张量/最终 logits 的误差摘要、生成 token 序列。保留首个分叉位置；先小输入和少量 token，再扩展到不同专家路径。
- 在**固定离线 PPL 文本**上测量相同 token 数的 PPL，并记录输入哈希及实际 token 数。不要把 `exact(lossless)` 占位串作为质量结果。
- 每次改同步/缓存代码先跑 CPU checks + L0，再在 A100 上跑短窗正确性。出现 NaN、路由或 token 分叉时保留原始证据并停止正式性能队列；浮点误差阈值必须预先写入协议，不能事后放宽。

**出口**：路由/token 一致，logits 在预设阈值内，PPL 对照一致；失败则定位并修复，再重新开始门禁。

### G2：公平性与计量门禁

- 按策略统计峰值 GPU `allocated/reserved`、模型 trunk/KV、expert pool、预取/近失缓冲；CPU 统计 pinned、pageable、镜像、staging、页缓存相关信息。对共享张量做去重记账，另留操作系统级 RSS/locked memory 快照。
- 统一物理 GPU/CPU 容量上限；超过上限的策略标为 `invalid_budget`，不能仅凭相同 `K_H/K_C` 宣称公平。若 50/40 GB 不安全，**全策略一起**选择新的安全预算并重新冻结，保留原运行作为诊断。
- 按 warmup、prefill、decode、PPL 分开统计：demand 到达前在 HBM/CPU/SSD 的来源，真实 SSD 读取次数/字节、H2D/D2H 字节、预取字节、重复读取、每阶段用时。保存 per-token 或 per-window 原始行和可复算聚合。
- 用人工可核的小 trace 验证各计数器，再用 A100 小样本检查：计数与实际读字节/缓存状态一致；预取不能被记作 demand HBM 命中。

**出口**：X7/X9 对应的物理账和阶段账可复核，介质可确认，正式主实验具备同预算口径。

### G3：单模型主结果与三项 Insight（A100 主队列）

按依赖顺序运行，所有策略共享冻结输入、模型、store、物理预算和同步语义：

1. **试跑与估时**：先选一个短输入、一个长输入，测各策略真实耗时和内存峰值；根据这些 pilot 估算队列，不用诊断运行的速度作论文结果。
2. **主对比**：未优化 fp16 单卡、普通三级 LRU、MECC，以及已核对原实现/本地适配的强对照。对照名称须明确“原系统复现”还是“机制适配”，不把本地适配称作原论文实现。问答、代码各至少三次独立运行；轮换策略运行顺序。
3. **Motivation I / Insight I**：冻结其余规则，只换初始专家位置；记录启动段 miss、TTFT 和 TPOT。用独立画像输入，不能从评估请求中提取热度。
4. **Motivation II / Insight II**：冻结同一初始计划，只换缓存更新规则；记录再访比例、逐次 SSD demand、物理字节与 TPOT。普通 H+C 全局 LRU 必须同场比较，以判断联合更新的独立增益。
5. **Motivation III / Insight III**：固定 A→B、B→A 和 A→A 三条顺序序列与窗口大小；记录每窗 SSD demand、TPOT、热专家位置。若真实路由没有明显变化，如实报告，不构造漂移。
6. **逐项消融与资源扫描**：从未优化版本开始，逐项加入初始放置、两级缓存更新、计算/传输重叠；CPU 预算扫描只选实际安全点，生成长度按实际 token 数分组。所有点至少三次。

**出口**：先填 Mixtral-8×7B 的主图、动机/Insight 和资源图；每项报告原值、中位数、离散度、失败次数。方向与理想目标不同时以实测为准。

### G4：跨模型与多卡（独立资源门禁）

- **第二/第三模型**：先核 loader、权重格式、fp16 专家总量、模型 snapshot、store 容量、单任务 CPU 预算、实际 SSD demand。每个模型先 G1/G2 小样本，再复制 G3 的核心主对比与 Insight 消融。无法通过门禁时保留 `blocked`，调整 PPT 横轴，不填估算柱高。
- **多卡完整驻留**：借用至少能完整驻留模型的多卡节点。锁定同模型、版本、精度、输入、生成参数与请求并发；分别测 2/4/8 卡可行配置的 TTFT、TPOT、吞吐及 GPU 数。若某卡数装不下，明确 `infeasible`。多卡结果只与单卡真实测量并列，不把 FlashMoE 等其他系统的论文数字当作同机对照。
- 如果无法获得多卡节点：第 4、6、16 页中依赖多卡实测的面板应重设计或明确标为“情景示意”，不能算实验图已补齐。

**出口**：跨模型/多卡图具备独立原始报告；或论文与 PPT 使用经过调整、全部由已完成实测支撑的图。

### G5：数据审计、作图和写作

- 对每个报告校验 `mode=real`、`platform`、`run_time`、运行 commit、config fingerprint、模型/输入 hash、真实 SSD demand、策略和物理预算。检查 `partial_result` 与 `result` 一致，失败与 OOM 保留在运行台账中。
- 先更新 `PROVENANCE.md` 的 claim↔证据表与未关闭矛盾，再运行 `python mecc_package/scripts/verify_claims.py`；对新图增加自动检查：每个点至少三条原始 run、无 `smoke`/诊断/占位来源、没有跨预算拼接。
- 将 PPT 和论文的作图脚本改为只读取**已核验的 figure manifest**。柱高用中位数，误差线按预先约定的 IQR 或原始点显示；图注明确模型、任务、预算、精度、重复次数和基线身份。保留原始理想示意版在独立目录，正式版不得读 `ideal_assumptions.json`。
- 最后逐页/逐图人工审稿：坐标、单位、图例、颜色、数据标签、文字叙述与 JSON 一致。重新渲染 PPT/PDF 与论文 PDF，再进行一次数据来源检查。

**出口**：所有保留的实验面板状态为 `measured_verified`，或已从正式版删去/重设计；论文和 PPT 不再含未标明的理想目标数值。

## 4. 单张 A100 的排期原则

一次独占 A100 **24 小时只够作为第一批时间窗口，不应承诺填满所有图**。最新诊断中一次短窗双策略 PPL 与一次 4×16 稳定性运行均需要较长的墙钟时间，而且正式实验还要求更多输入、策略和重复。实际排期以 G3 的试跑计时为准：

1. 第一个窗口优先 G1/G2；任一门禁失败，停止性能队列，修复后再试。
2. 门禁通过后，优先 Mixtral-8×7B 主对比与 Motivation I/Insight I；有余时依次做 II、III。
3. 不把三次重复压缩成一次，也不删掉失败记录来满足窗口；未完成部分排入后续 A100 窗口。
4. 估时公式：`每臂试跑耗时 × 实际图格数 × 3 次重复 + 模型加载/冷盘准备 + 20% 故障余量`。每个阶段结束重算，避免用理想目标推断运行时长。

## 5. 本地与 Workbuddy 的交接

**本地负责**：冻结实验协议；实现 G1/G2 的只读追踪和图格配置；CPU 检查；审查每轮报告；维护证据表及作图脚本。任何缓存算法优化先按 [OPTIMIZATION.md](OPTIMIZATION.md) 登记，不能与正式实验的计量补丁混在同一次单变量比较中。

**Workbuddy 负责**：在干净 checkout 和独立 `gpu/a100-*` 分支上，按每轮冻结配置 dry-run → 主机/GPU 空闲检查 → L0 → A100 运行 → 导出紧凑报告 → 提交推送。每轮只接收一个明确工作包；异常即报告并停止，不自行改预算、输入、模型、预取或精度。

每个图格的报告至少包含：`run.json`、`status.json`、`result.json`、命令、输入/模型 hash、计数器原始行、日志尾、失败原因及重复编号。大型完整日志留远端，不提交权重和 store。回传格式为 `branch / commit / run IDs / 完成与失败图格 / 阻塞项 / 下一步建议`。

**当前可执行工作包**：[WORKBUDDY_A100_G1_CORRECTNESS.md](WORKBUDDY_A100_G1_CORRECTNESS.md) 已冻结同仓库 fp16 策略的逐层路由/logits/token 和离线诊断 PPL 比较。其结果只关闭 G1 的第一层内部一致性门禁；随后由本地实现 G2 的物理字节及分相位计量，再发布下一轮 A100 执行文档。

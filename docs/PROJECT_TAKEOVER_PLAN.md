# MECC 项目接管与推进路线图

> 版本：2026-07-18
> 定位：本文件是接管后的**执行层总计划**。各领域的具体规范仍以
> `APPLICABILITY.md`、`EXPERIMENTS.md`、`OPTIMIZATION.md`、`THEORY.md`、
> `PROVENANCE.md` 和 `PAPER_WRITING.md` 为准；本文件不替代这些权威文档。

## 1. 接管目标

MECC 已经具备方法、实现、真机数据和论文雏形。接管后的目标不是继续无边界堆功能，
而是把它推进成一个同时满足以下条件的科研系统：

1. **论点准确**：只在“模型 expert 总量大于可用 CPU 内存、必须落 SSD”的主场景宣称有效。
2. **证据可信**：每个对外数字都有可定位的 D2/D1/D0 证据、平台、时间、配置和生成命令。
3. **实现可复现**：从环境检查、模型/store 准备到 L0/L1/L2 均有稳定入口，断连不丢实验。
4. **方法可解释**：编译期放置与运行期联合 LRU 的贡献能够被理论、消融和端到端结果分别支撑。
5. **论文可投稿**：贡献边界、baseline、公平性、局限、理论状态和引用均经得住审稿。
6. **工程可演进**：核心库与论文 harness 职责清晰，新优化可单变量接入、验证和回退。

最终交付物是“一条闭环证据链”，而不只是一个更快的实现：

```text
适用性边界 → 方法与命题 → 实现锚点 → 可复现实验 → 数据溯源 → 论文 claim
```

## 2. 不变原则与决策顺序

### 2.1 科研定位

- 主战场判据只有一个：`expert 总量 > 可用 CPU 内存`。
- Mixtral-8x7B 是当前 L2 主验证模型；DeepSeek-V2-Lite 仅为 L1 对照。
- L0 只验证逻辑，D1 模拟器只说明趋势，只有 L2/D2 能支撑主性能结论。
- 无损是方法定义的一部分；量化、剪枝等改变数值的方案只能作为有损 baseline。

### 2.2 工作优先级

任何新工作按以下顺序裁决：

1. **正确性与科研诚实**：是否会破坏无损、适用性或证据口径？
2. **可复现性**：能否稳定生成带完整元数据的结果？
3. **论文价值**：是否补强核心 claim 或消除明显审稿风险？
4. **端到端收益**：是否在 L2 主场景产生可解释净收益？
5. **工程优雅性**：最后才是抽象、重构和代码美观。

### 2.3 明确不做

- 不用 L0 tok/s、D1 模拟器或 D0 理论值包装真机加速。
- 不从已舍入的历史 tok/s 反推更精确 speedup。
- 不为了“更好看”静默修改矛盾数字、平台或历史 JSON。
- 不同时实现多个优化后再做一次总对比；必须单变量消融。
- 不在没有 L2 证据时把 candidate 写成 adopted。
- 不凭记忆补论文引用；未核实项保留 `[TODO: verify cite]`。

## 3. 当前基线（接管时点）

### 3.1 已具备

- `compiler.py` 与 `compile.py` 两套编译入口；根级库文件依赖关系已受保护。
- `mecc_framework/` 模块化核心库与 `e2e/` 论文主表 harness 并存。
- 四策略 `ours / swapmoe / fiddler / naive` 可在真实 Mixtral 路径运行。
- 当前权威 L2/D2 主证据为 `results/raw/mixtral_real.json`：PROVENANCE M1--M5 已 verified。
- L0、实验分级、优化分类、理论状态、数据溯源和论文写作均已有规范。
- 吞吐精度、平台/时间元数据与离散 Zipf α 估计已修复，并有 CPU 回归测试。

### 3.2 主要缺口

| 类别 | 缺口 | 风险 |
|------|------|------|
| 证据 | 两个较新 Mixtral JSON 缺平台/时间；部分 DeepSeek 论文数字无 JSON | 对外数字不可核验 |
| 口径 | README、旧论文、STRATEGY 和个别注释仍可能混用 A100/5090、1.33×/1.62× | 叙事自相矛盾 |
| baseline | SwapMoE 的“有损/无损、两级/三级”描述在不同文档中不完全一致 | apples-to-apples 可信度受损 |
| 理论 | 接管时 TH-004/005 为 partial、TH-006 为 conjecture；现 TH-004 已证明，TH-005/006 普遍版已反驳 | 论文必须删除普遍优势定理口吻，改为条件性经验观察 |
| 实现 | 核心库与 e2e 有重复缓存实现，行为漂移缺少自动对照 | 修改可能只修一套路径 |
| 实验 | 长实验依赖人工终端；正式主表成本高、失败恢复弱 | 复现效率低、容易丢作业 |
| 评测 | 更强 baseline、长上下文与任务精度尚未形成正式证据 | 论文覆盖面有限 |
| 论文 | 原稿与示例论文、PROVENANCE/THEORY 的最新状态未完全同步 | 投稿风险高 |

## 4. 总体路线

```text
P0 基线冻结与一致性
        ↓
P1 可复现实验与证据基础设施
        ↓
P2 核心 claim 补强（baseline + 消融 + 理论）
        ↓
P3 单变量性能优化
        ↓
P4 论文收敛与发布
```

阶段按门禁推进，而不是按日期强行推进。前一阶段未通过时，不把后一阶段结果写进主结论。

## 5. P0：基线冻结与一致性清理（最高优先级）

### 5.1 目标

建立一个全仓唯一、可机器检查的“当前事实快照”，先解决审稿人最容易发现的矛盾。

### 5.2 任务

1. 逐项核查 README、STRATEGY、论文原稿、示例论文和结果 README 中的：
   - 主平台 A100/5090；
   - 1.33× 综合吞吐与 1.62× TPOT；
   - SwapMoE 是否量化、是否无损、CPU/SSD 语义；
   - Mixtral expert 336MB 实测张量与 1407MB 理论口径。
2. 所有冲突先登记到 PROVENANCE，再定采信口径；历史文件不静默覆盖。
3. 扩展 `verify_claims.py`，让高风险文本 claim 也能被自动检查，而不只核 JSON 字段。
4. 给重要实验配置生成稳定的 config fingerprint，记录模型 revision、代码 commit、预算、策略和 prompt 参数。
5. 整理工作区中未登记的 baseline、报告与预检文件：只分类和登记，不删除用户文件或历史结果。

### 5.3 交付与验收

- `verify_claims.py`：0 FAIL；所有 WARN 都能在 PROVENANCE 找到负责人/处置状态。
- 主场景平台、性能口径、baseline 精度语义在所有对外文档一致。
- 任意主 claim 可在 3 次跳转内定位到：claim → PROVENANCE → JSON 字段/生成命令。
- 产出一次“投稿前事实快照”提交，后续新工作基于该提交分支推进。

## 6. P1：实验可复现性与证据基础设施

### 6.1 目标

让长时 GPU 实验在断连、重启或失败后仍可接管，并确保每次运行自动留下完整证据。

### 6.2 任务

1. 新增统一实验 launcher，支持：
   - 用户级 systemd/tmux 持久运行；
   - 固定 unit/run id；
   - PID、日志、JSON、代码 commit、环境快照自动落盘；
   - `status / stop / resume-from-store`；
   - 禁止同 GPU 重复启动冲突作业。
2. 把 L0/L1/L2 的参数模板变成显式配置文件，避免 shell 默认值漂移。
3. 为 85GB Mixtral expert store 增加 manifest、完整性校验和模型 revision 绑定，避免复用错误 store。
4. 在 `run_e2e.py` 增加失败时的阶段性状态文件；最终 JSON 采用临时文件完成后原子改名。
5. 建立结果 schema 校验：策略覆盖、必采指标、命中率合计、平台/时间、模式和 PPL 语义。
6. 建立两套实现的一致性测试：同一微型 trace 下，核心库与 e2e 对命中/升降级的语义一致。

### 6.3 交付与验收

- 断开 SSH/Codex 后，L2 服务继续；重新连接后一条命令恢复状态。
- 已物化 store 可跳过重复生成，并通过 manifest 校验。
- 失败运行不会留下看似完整的主表 JSON。
- L0 在 CPU CI 中自动运行；无需 GPU 的统计、schema、编译器测试全部进入测试入口。

## 7. P2：补强核心科研 claim

P2 分为评测、理论和实现语义三条并行但独立验收的主线。

### 7.1 Baseline 公平性审计

1. 为四策略写一份逐项语义矩阵：精度、HBM/CPU/SSD 容量、淘汰、CPU 命中、SSD miss、预取。
2. 用单元 trace 验证每个策略确实执行文档描述的行为。
3. 明确 SwapMoE 对比有两种可能口径：
   - 无损、同三层预算的策略机制对比；
   - 论文相关工作的量化版本，作为有损速度/质量折中对比。
   两者不得共用一个模糊标签。
4. MoE-Infinity 等新 baseline 在完成版本锁定、配置对齐和最小正确性测试前保持 inactive。

**验收**：每个 baseline 的结果行都能说明“同预算、同精度或明确标注精度差异、同输入、同平台”。

### 7.2 核心消融

优先回答“为什么有效”，而不是继续追逐一个总加速数字：

1. 编译期静态放置 vs 随机/均匀放置；
2. 联合 HBM+CPU LRU vs 静态 CPU tier；
3. 冷 SSD vs warm page cache；
4. 不同 CPU budget 下的适用性边界曲线；
5. 稳态与热点漂移分开报告，模拟器与真机分表。

**验收**：每项消融只有一个变量变化，产物包含 JSON、日志、配置和解释；负结果同样登记。

### 7.3 理论攻关

建议顺序不是直接证明最强命题，而是先寻找反例、收窄陈述：

1. **TH-006**：先检验“联合 LRU 对任意动态+静态拆分都包含”是否过强；构造短 trace 穷举反例。
2. 若原命题被反驳，改写为带 IRM/Zipf/稳态或 drift 条件的可证明版本，状态标 `refuted/partial`。
3. **TH-005**：把“静态 CPU 命中趋零”改为带工作集、K_H 和访问分布条件的定量界。
4. **TH-004**：区分“固定独立 HBM/CPU 容量下的按秩填满”与“共享预算下的边际平衡”，补交换论证。
5. α MLE 增加有限样本偏差、置信区间和 profile 外推误差实验，不把给定排序后的 MLE扩大成无偏估计。

**验收**：只有完整证明且通过反例检查的命题标 `proven`；理论变化同步更新代码锚点和论文口吻。

## 8. P3：性能优化路线

只有 P0/P1 基础稳定后才进入性能优化。所有项目遵循 `OPTIMIZATION.md` 的单变量流程。

### 8.1 推荐顺序

| 顺序 | 项目 | 类型 | 原因 | 主要门禁 |
|------|------|------|------|----------|
| 1 | `async_ssd_read` | B 工程 | 直接隐藏主瓶颈 SSD 冷读 | L2 TPOT/tok·s 净收益，PPL 不变 |
| 2 | `batch_prefetch_plus` | B 工程 | 基于已有预取骨架，改动较局部 | 预测命中率与 PCIe 浪费均可解释 |
| 3 | `pinned_buffer_pool` | B 工程 | 可减少注册/分配开销 | pinned 常驻不得挤占 K_C 导致净退化 |
| 4 | `routing_aware_placement` | A 算法 | 直接压低 SSD 命中 | L1 只看上界，必须 L2 定论 |
| 5 | `adaptive_alpha` | A 算法 | 对 drift 有潜力 | 稳态不退化、无 thrashing |

### 8.2 每项优化的固定流程

```text
写假设 → 建基线 → 单变量实现 → L0 正确性 → L2 消融 →
解释 delta → adopted/rejected/parked → 更新注册表和证据
```

停止条件：PPL/输出不一致立即回退；L2 净收益不正或不可解释时不保留；micro-benchmark 提升但端到端退化时以端到端为准。

## 9. P4：论文与发布收敛

### 9.1 论文结构

论文按 `PAPER_WRITING.md` 收敛，不新增超出证据的 claim：

- Abstract/Introduction：只使用 verified D2 主场景结论。
- Motivation：突出“CPU 也装不下、SSD 被迫进入关键路径”。
- Insight/Method：TH-004/005/006 按真实状态降口吻。
- Experiment：L2、L1、D1 分区；平台、精度和预算写清。
- Discussion：主动写适用边界、理论缺口、baseline 限制与结果成本。

### 9.2 发布门禁

1. `verify_claims.py` 无 FAIL；所有主数字 verified。
2. 论文表格可由 JSON 自动生成，禁止手工抄数。
3. 所有引用完成外部核验；无虚构 bib 条目。
4. 从干净环境完成一次 L0；L2 复现包包含 config、commit、manifest 和运行说明。
5. README、论文、PROVENANCE、THEORY 的平台与口径一致。
6. 归档版本打 tag，历史结果只读保留。

## 11. 风险登记

| 风险 | 早期信号 | 应对 |
|------|----------|------|
| 主 claim 依赖单一实验 | 新配置下波动大 | 保留权威值，补重复与置信区间后再更新 |
| baseline 语义不公平 | 同名策略在代码/文档中含义不同 | 先做语义矩阵与 trace 测试 |
| 长实验成本过高 | 预检数十分钟、正式运行数小时 | 两阶段预检、持久服务、复用 store、原子结果 |
| 页面缓存污染冷 SSD | cold/warm 结果差异异常小 | 记录 cache 状态，冷/热分开，不混口径 |
| GPU/CPU 内存顶满 | Fiddler 接近 80GB、RSS 过高 | 预检峰值、预算留安全边际、失败记录 |
| 两套实现漂移 | L0 过但论文 harness 行为不同 | 共用 trace 与语义一致性测试 |
| 理论命题过强 | 短 trace 可构造反例 | 先反例搜索，再收窄条件，诚实降级 |
| 论文先于证据更新 | 表格与 JSON 不一致 | JSON 自动生成表格，发布前机器门禁 |

## 14. 成功定义

项目成功不以“又得到一个更大的加速数字”为唯一标准，而以以下组合判断：

- **可信**：主结论没有未登记矛盾，数字与理论均不越级。
- **可复现**：别人能从固定 commit 和配置复现逻辑与主证据。
- **有解释**：SSD 命中、tier 延迟和端到端收益形成因果链。
- **有边界**：明确知道方法在何处无效，不夸大小模型场景。
- **可扩展**：新 baseline、benchmark、优化和命题可以注册、验证、回退。
- **可投稿**：论文的每条贡献都有代码、实验或严格命题支撑。

这份路线图的核心策略是：**先把事实和复现基础做硬，再补强核心贡献，最后追求性能与论文表达。**

1. SwapMoE：让内存预算成为显式的设计输入

Motivation

MoE 的专家数量随模型规模增长，但边缘设备的可用内存很小。全部专家留在内存会放不下；每次按需读取会增加推理延迟；永久删去专家又会损失质量。SwapMoE 把问题表述为一个预算内的内存—速度—质量权衡。论文 §2

Insight 与方法机制

Insight：服务系统不必在每个时刻保留所有真实专家，可以维护一组重要的“虚拟专家”，并随输入变化更新它们与真实专家的对应关系。 系统先做细粒度专家画像，估计访问和质量影响；内存规划器决定不同层应保留多少虚拟专家以及更新频率；运行时根据输入调整映射。原论文采用遗传搜索寻找满足内存与延迟约束的配置。这样的设计把“哪些专家值得占据设备内存”从固定模型结构中解耦出来。论文 §3

2. Fiddler：一次专家未命中，也许应搬激活而非搬权重

Motivation

GPU 显存容不下完整 Mixtral 时，CPU 中的专家权重搬到 GPU 会经过 PCIe；对某些请求，把较小的激活发给 CPU 执行可能更快。但 CPU 计算能力和批处理效率与 GPU 差别很大，固定一种执行方式无法覆盖短请求、长 prefill、beam search。论文引言与 §3

Insight 与方法机制

Insight：专家执行位置应由“搬权重到 GPU 的总时间”与“在 CPU 上算并同步的总时间”共同决定。 Fiddler 根据工作负载和设备特征确定执行计划，并利用专家使用频率放置常用权重。长 prefill 往往使 GPU 计算更划算，batch 很小或生成方式不同则可能让 CPU 路径有优势。它的研究轴是计算位置选择，与缓存替换相关但不相同。论文 §3

3. MoE-Infinity：看一条请求内部的激活模式

Motivation

个人机器上的 batch=1 推理与大规模在线服务不同：同一请求生成多个 token 时，专家激活常呈现稀疏的重复模式。只按最近使用时间替换，或只按全局频率预取，可能让下一层马上需要的专家被挤出缓存。论文 §4.1—4.2

Insight 与方法机制

Insight：一条请求的逐层专家激活轨迹，比全局热度更能提示接下来需要保留或预取什么。 MoE-Infinity 构建 request-level Expert Activation Matrix（EAM），从历史轨迹中挑选与当前请求相似的模式；再结合层的位置为缓存对象赋予优先级，并据此替换、预取。它在论文示例中解释了为什么传统 LRU 可能过早逐出下一层所需专家。论文 §4.5—4.7

4. MoE-Lightning：高吞吐推理是调度问题

Motivation

离线批量生成时，模型权重交付、CPU 工作、GPU 工作如果串行发生，会浪费各设备的空闲时间。批大小、prompt 长度、输出长度又会改变瓶颈位置，固定调度难以持续接近高吞吐。论文 §3

Insight 与方法机制

Insight：通过 CPU/GPU/I/O 流水和性能模型一起选配置，可以让权重交付与计算彼此覆盖。 MoE-Lightning 的 CGOPipe 组织流水，paged weights 管理权重；Hierarchical Roofline Model（HRM）比较不同层级的带宽、算力与工作负载，以选择批大小、设备分工和交付策略。多卡时它还使用节点内张量并行。论文 §4

5. SSD-LLaMA：将磁盘变成可执行专家的来源

Motivation

量化后的超大 MoE 仍可能超过消费级显存和主存。磁盘容量足够，但一次专家执行需要经过 I/O、主存保留和显存交付；单独优化某一段未必改善端到端速度。论文原文

Insight 与方法机制

Insight：磁盘 I/O 管线、三级驻留和 CPU/GPU 计算分工需要一起测量与协调。 SSD-LLaMA 按专家组织高效读取，动态管理磁盘—主存—显存中的权重，并按实际端到端时间选择专家在哪个设备执行。其论文所述主配置执行每个路由器选中的专家。对于 DeepSeek 平台，论文的 CPU/GPU 分工扫描发现“全部选中专家在 GPU 上算”比测试过的 CPU 分工更快，因此把 CPU 留给 I/O、缓存和调度。论文 §4.3—5

6. FlashMoE：最近性加频率，比单独 LRU 更会挑淘汰对象

Motivation

专家访问既有短期连续性，也有长期热度。LRU 只看最近一次，LFU 只看累计次数；在有限内存下，错误淘汰会反复触发磁盘读取。论文 §2—3

Insight 与方法机制

Insight：把最近性和频率作为特征，让轻量模型学习专家的未来重用距离，可直接优化缓存替换。 论文用 1/recency 和归一化 frequency 作为输入，以 Belady 最优替换产生训练标签，训练约 113 KB 的逐层 FFN。模型加载时只先装非专家权重，专家按需交付。训练路由轨迹来自 TriviaQA 的 512 条样本，每条最多 512 token。论文 §3、算法 1

7. MoE-CORE：把逐层容量、画像和预取协同起来

Motivation

不同层的专家权重大小、路由热度和访问时序不同。统一按层分配相同缓存槽位，会让一些层闲置、另一些层频繁搬运；prefill 与 decode 的访存形态也不同。论文 §1—2

Insight 与方法机制

Insight：prefill 适合整层交替装载，decode 适合逐层非均匀驻留并预测下一层需求。 MoE-CORE 在 prefill 用两个交替缓冲重叠权重传输与计算；decode 结合任务领域画像生成初态、按层安排不同缓存容量、使用路由历史更新驻留，并跨层预取。主要对比运行路由器选中的原专家；论文另列可选的近似专家替换及多 token 预测实验。论文 §3

8. FlashMoE（Aimuyo 等）：专家已在多卡显存，为什么 GPU 仍会等待

Motivation

专家并行把同一 MoE 层的不同专家分散在多张 GPU 上。路由器选定专家后，系统要把 token 送往持有专家的 GPU，再把计算结果送回。传统实现常把门控、分发、专家计算和合并拆成许多 kernel；通信同步与 kernel 启动间隙让 GPU 空闲。这与 Kim 等人同名 FlashMoE 所研究的 SSD 缓存替换是两个问题。论文 §1—2

Insight 与方法机制

Insight：在多卡全显存条件下，把分发、专家计算和合并放进同一个常驻 GPU kernel，可以细粒度重叠通信与计算。 FlashMoE 由 GPU 发起跨卡通信，用 tile 级任务调度决定计算何时进行。专家权重驻留在 GPU，跨卡主要移动 token 激活；它优化的是完整 MoE 层的执行路径，而非从 CPU 或 HDD 按需加载专家权重。论文 §3

对 MECC 的启发。 一旦多卡总显存能容纳专家，主要瓶颈可能转向 token 通信与算子调度。若总显存不足，再采用 CPU／磁盘卸载时，专家权重传输重新进入关键路径。MECC 的单卡 HDD 问题属于后一类容量条件，因而多卡 FlashMoE 适合解释部署路径，不适合作为未重跑的直接性能基线。

阅读这些实验时，先核对哪些条件

比较两张实验图时，先看模型与权重格式，再看GPU、CPU 和磁盘预算，接着看benchmark、批量和输出长度，最后看指标是 TTFT、TPOT、tok/s、总吞吐、命中率还是质量。多卡 FlashMoE 测的是专家已驻留时的 MoE 层执行；其余卸载系统常测完整模型请求。它们回答的问题不同，实验数字也不能直接放在同一根柱上。

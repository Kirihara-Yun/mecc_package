# 从文字修订转向技术增量

本清单针对第四轮仍阻止 5 分的内容。理想曲线继续保留，不把补实测作为本轮未达标的理由。下面的设计均为下一步建议，不是已实现、已证明或已获得性能收益的机制。

## 1. 把物理主存约束纳入编译决策

当前 HBM 与 CPU 槽位分别分配，但 HBM 中每个专家还有 CPU 镜像。主存既保存 CPU 主驻留专家，也保存 HBM 专家的镜像。编译器的两个独立槽位上限因此不等同于实际主存上限。

一个可研究的增量是联合决定：每层 HBM 槽位、CPU 主驻留槽位、哪些 HBM 专家保留镜像。目标函数同时计入冷读、H2D、没有镜像时的 D2H，以及初始化开销。资源约束按唯一物理存储计数，并留出 staging。镜像保留与 CPU victim 保留会竞争同一份 host 预算，这才是当前按热度分别填槽位没有表达的决策。

要完成这个增量，先明确字节约束和代价模型，再给出与代码一致的求解步骤。不能只在现有公式中增加镜像符号，也不能未经证明就声称全局最优。现有 THEOREM 的独立 tier 容量结论不自动覆盖这个共享约束。

## 2. 闭合画像与执行接口

- `e2e/run_e2e.py` 的非 uniform 分支目前生成 per-layer alpha。应接入独立画像输出并保存估计参数、排序、输入来源及 plan 哈希。uniform 继续作为对照。
- `policy_plugin.py:OursIOPolicy` 的 GPU entry 与公共镜像/淘汰函数需要使用同一种表示。该问题属于实现契约，不通过改论文掩盖。
- prefill 的并行读盘与 decode 的按需加载应作为独立调度模式。若要主张 decode overlap，需要实现相应依赖和容量管理；不能直接把 prefill 示意图当作该模式已经存在。

这些是本地可开发内容，不需要先取得新的 A100 结果才能明确设计。

## 3. 写清技术问题，而不是增加功能维度

最需要回答的是：在同一组物理容量、初始 ID 和 delivery 条件下，MECC 的编译输出增加了什么可解释的收益或资源可行性。SSD-LLaMA 的 RAM/VRAM 保留和 MoE-CORE 的画像/在线机制必须作为已存在的能力来对照。把 HDD 换成更慢的介质、增加几个勾号、或提高理想柱高，均不构成这个区别。

可选择的研究结果包括：共享 host 预算下的可行放置、镜像/回迁选择、或对任务切换后有限服务区间的代价分析。需要先做出其中一个实质结果，再更新贡献和主图。当前文稿没有把这些建议冒充为已有工作。
